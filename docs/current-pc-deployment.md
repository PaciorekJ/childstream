# Recommended current-PC deployment

**Selected arrangement:** one Windows parent console plus its exact parent-associated loopback child session; a limited ChildStream agent, portable ChildStream-owned Sunshine, Steam and the game run inside that child. The existing native Sunshine service, VDD and parent desktop remain owned by their current operators. Moonlight on Fire TV or phone connects only to the ChildStream port family after a separate LAN plan is approved. This is the single-PC product path, conditional on real Stage A/B and resource tests; it is not an accepted deployment on the intended workstation today.

The controller path is deliberately a selected **configuration with an unpassed acceptance gate**, not a virtual-controller implementation. Sunshine remains the only streaming/input engine. The pinned [Sunshine configuration](https://docs.lizardbyte.dev/projects/sunshine/v2026.914.233613/md_docs_2configuration.html) supports the explicit gamepad driver, controller, audio sink, display and network settings used here. A live child-only gamepad claim requires parent and child observers plus the actual game input API; the presence of a PnP device or a successful software fixture cannot substitute for it. If the parent consumes child controller reports, this configuration is rejected. Parent desktop, input and audio noninterference are requirements, not negotiable acceptance criteria.

The pinned [Sunshine Windows audio implementation](https://github.com/LizardByte/Sunshine/blob/v2026.914.233613/src/audio.cpp) compares the chosen sink to its current default and can call `set_sink`; its [Windows backend](https://github.com/LizardByte/Sunshine/blob/v2026.914.233613/src/platform/windows/audio.cpp) uses `SetDefaultEndpoint` for all roles. It can auto-detect Steam Streaming Speakers even when `virtual_sink` is absent. ChildStream's new default-endpoint equality check removes one source of switching but cannot control the Moonlight host-playback flag or prove the Windows default is session-local. A later upstream [capture-only `external_audio` option](https://docs.lizardbyte.dev/projects/sunshine/master/md_docs_2configuration.html#external_audio) is documented on master, but is absent from the pinned release and cannot be assumed in this build. The smallest existing-technology correction is a reviewed, integrity-pinned Sunshine release that actually supports capture-only mode, coupled to an independently verified child-only render endpoint; do not put an unsupported key into the current pinned config. If that combination cannot preserve the parent default and output during real streaming, reject audio in this deployment.

**Current-PC stop condition:** do not enable child sessions while the existing connected-network RDP posture lacks containment, and do not require a parent sign-out that interrupts protected work. A VM on this Windows 11 Pro PC is not the selected deployment; no VM creation is authorized. If the two-session controller test shows parent consumption, reject this configuration. If audio separation fails, reject this configuration until an established capture-only Sunshine release and child-only render endpoint can be independently qualified. Do not add a custom driver, game hook or privileged service by default.

## One bounded, unexecuted Windows qualification proposal

This proposal creates no authority to run commands. The elevated, read-only host result is `ChildSessionsEnabled=False`. The connected-network baseline has 20 potentially RDP-permissive and six unknown firewall rules; there is **no accepted exact plan hash** and no proven containment of a listener that feature enablement might create. The first gate is an independently reviewed, noninterfering ordinary-RDP containment mechanism effective before any feature write on every connected interface and internal guest path. A narrowly scoped temporary block for the TermService port family could be considered only after verifying effective policy, allowed RDP dependencies and exact rollback without inspecting or interrupting protected work. If that cannot be demonstrated, the intended-PC feature experiment remains No-Go. Existing Sunshine, VDD, networking, Docker, WSL and Tailscale are untouched.

After that gate passes and the owner separately approves an exact plan hash, the bounded Stage A effect would be one journaled machine-wide `WTSEnableChildSessions(true)` from observed False, read-only feature/WTS/listener verification at the physical console, and exact restoration to False. Ordinary network RDP must stay denied throughout; stop immediately on unexpected TermService/listener changes, error 1168, ambiguous feature state, or journal drift. Do not reconnect or remove a temporary containment measure until the feature and listener baseline are independently restored. A failed restore leaves containment in place for reviewed recovery, without further child creation.

Microsoft's [child-session documentation](https://learn.microsoft.com/en-us/windows/win32/termserv/child-sessions) describes an automatic-authentication exception when the parent logged on before enablement. Test the API result first; a fresh parent sign-in is a possible one-time setup step, never a routine launch or Moonlight-pairing step. On this protected workstation, if the experiment requires sign-out or fresh sign-in that would interrupt unrelated work, stop and restore without signing out. A separately approved Stage B would permit one loopback viewer connection, simultaneous parent/child desktop interaction checks and exact-child teardown under the same verified containment, followed by independent feature/listener restoration. Controller, audio and GPU/streaming tests follow only if Stage B passes and each parent-noninterference gate is separately met.
