# Child-only controller routing decision

ChildStream currently sets `controller = disabled` in its pinned Sunshine configuration. This is a **missing product function**, not a completed software function awaiting only a hardware check. The separately compiled `ChildStreamControllerWitness.exe` is opt-in, read-only observation code; it is never invoked by ordinary startup or installed as a device provider.

The [pinned Sunshine input implementation](https://github.com/LizardByte/Sunshine/blob/v2026.914.233613/src/platform/windows/input.cpp) creates ViGEm targets with `vigem_target_x360_alloc` or `vigem_target_ds4_alloc` and attaches them with `vigem_target_add(client, target)`. That call has no Windows logon-session parameter. The `gamepad_id_t` indexes in that path refer to Sunshine client/gamepad slots; source review found no operation there that assigns an emulated device to the child WTS generation or hides it from the parent desktop. This is an inference from the reviewed provider path, not proof that all possible Windows input architectures are impossible. [Sunshine's pinned configuration](https://docs.lizardbyte.dev/projects/sunshine/v2026.914.233613/md_docs_2configuration.html) documents `controller` and `gamepad_driver = vigembus`, and says ViGEmBus supports only Xbox 360 and DualShock 4 profiles. Merely setting those options or detecting a driver would create a machine-visible controller without establishing child-only routing.

The exact [ViGEmClient `vigem_target_add` contract](https://github.com/nefarius/ViGEmClient/blob/master/include/ViGEm/Client.h) accepts a bus connection and target pointer; target removal is equally process/bus scoped. Neither operation names a Windows session. The [HidHide API](https://docs.nefarius.at/projects/HidHide/API-Documentation/) hides device instance IDs and allows executable *paths* to see hidden devices. A path allow-list cannot distinguish an identical game executable in parent and child logon sessions, and changing the global hiding lists would affect unrelated input. Neither contract currently establishes child-only delivery. The precise missing enforcement boundary is an independently verifiable binding of each owned target instance to the exact child logon generation, or another supported device-access/report path that prevents the parent from receiving that target while preserving unrelated devices. It must also map both Moonlight controller reports separately, survive reconnect predictably, and remove only owned targets on disconnect/teardown. A stream client ID, XInput slot, feeder PID or shared Windows SID is not this proof.

The witness uses [XInputGetState](https://learn.microsoft.com/en-us/windows/win32/api/xinput/nf-xinput-xinputgetstate) and records the returned API code, not `GetLastError`: success, `ERROR_DEVICE_NOT_CONNECTED` (1167), and other read errors remain distinct. Each line records its **own** PID, Windows session, WTS logon time, monotonic timestamp, and four XInput slot states. Its target labels are explicitly declared and `targetAttribution` is always `UnresolvedByXInput`; XInput exposes only indices 0–3 and cannot identify a ViGEm instance. Synthetic tests check two distinct exclusive button-pulse sequences, disconnect/reconnect, ambiguous readings and logon-generation reuse. This is an acceptance aid, not routing functionality or proof that a game using another API is isolated.

After separate authorization on a test target, the opt-in read-only command is `ChildStreamControllerWitness.exe --observe --session <own-session-id> --logon <own-WTS-logon-time> --targets <declared-owned-A>,<declared-owned-B>`. Run it independently in each exact parent/child session; it refuses a mismatched session generation and emits 20 time-stamped four-slot snapshots over about two seconds. Declared labels are contextual only. The shipping app never invokes this command, and neither this command nor the synthetic matcher sends an input report.

For a separately authorized Stage B-capable Windows target, run a bounded two-session visibility experiment **before GPU/Moonlight validation if necessary**. First record each session's witness baseline and exact target instance IDs through a reviewed provider; separately approve creating two targets and sending distinguishable pulses one at a time. Compare child and parent witness output while parent focus changes, repeat after disconnect and a new child logon generation, and inspect the game's actual input API before claiming gameplay isolation. If a parent process can read either target, reject that provider. The remaining prerequisite is a provider contract or measured OS/device-filter behavior that binds exact owned instances to the child without global interference. No real witness run, driver change or injection is authorized on the protected workstation.
