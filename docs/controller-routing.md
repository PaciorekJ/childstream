# Child-only controller routing: implementation decision

**Decision:** the [current-PC deployment](current-pc-deployment.md) selects pinned Sunshine with its free ViGEmBus-only configuration, but no controller provider can be enabled safely from the reviewed contracts. ChildStream keeps Sunshine controller input disabled. The missing property is prevention of parent-session consumption of the child's two controller reports, including focus changes and reconnects. Provider ownership of a feeder or target does not provide this property. No adapter or injection was added on this unsupported premise.

## Exact pinned path

Sunshine is now pinned to official audio prerelease [v2026.1015.174736](https://github.com/LizardByte/Sunshine/tree/v2026.1015.174736). Its gitlinks resolve to [libvirtualhid ecc82912810fe09957abb9b8824255381a5f0fdf](https://github.com/LizardByte/libvirtualhid/tree/ecc82912810fe09957abb9b8824255381a5f0fdf) and [ViGEmClient 8d71f6740ffff4671cdadbca255ce528e3cd3fef](https://github.com/LizardByte/Virtual-Gamepad-Emulation-Client/tree/8d71f6740ffff4671cdadbca255ce528e3cd3fef). The detailed provider analysis below was performed against the previous Sunshine pin and its older libvirtualhid gitlink; it remains a conservative reason to keep controller reports disabled, not a fresh qualification of the new libvirtualhid revision. ViGEmBus is not bundled. We did not inspect installed drivers on the protected workstation.

Moonlight's per-client reports reach Sunshine's client/global gamepad slots. On ViGEm, the [pinned client implementation](https://github.com/LizardByte/Virtual-Gamepad-Emulation-Client/blob/8d71f6740ffff4671cdadbca255ce528e3cd3fef/src/ViGEmClient.cpp) adds a target to an open bus, assigns a bus serial, and uses that serial for report, feedback and unplug IOCTLs. Its target index returns that serial; a separate call asks for an XInput user index. Neither is a WTS logon generation or durable PnP instance identity. The [ViGEmBus driver project](https://github.com/nefarius/ViGEmBus) describes software USB controllers detectable by ordinary games. In its [driver source](https://github.com/nefarius/ViGEmBus/blob/master/sys/Driver.cpp), the field named SessionId is allocated on a bus-file open and used to unplug that file's child devices on close. It is a bus ownership number, not a Windows logon session. This upstream driver source is architectural evidence, not verification of the unknown installed driver version.

For libvirtualhid, the [pinned broker](https://github.com/LizardByte/libvirtualhid/blob/53e1a949fc0784af716b782ddfa6c647cafd1f05/src/platform/windows/broker/libvirtualhid_broker.cpp) authorizes creation using a machine license, records the owner process and exact driver device ID, and uses a random device token for update/destroy. Its [driver documentation](https://github.com/LizardByte/libvirtualhid/blob/53e1a949fc0784af716b782ddfa6c647cafd1f05/docs/windows-driver.md) describes generic VHF HID children and a separate Xbox 360 XUSB interface. The [Xbox companion driver](https://github.com/LizardByte/libvirtualhid/blob/53e1a949fc0784af716b782ddfa6c647cafd1f05/src/platform/windows/driver/libvirtualhid_xbox360_umdf.cpp) checks the private token for report submission, but XUSB state reads and input waits have no child-logon check. Its [INF](https://github.com/LizardByte/libvirtualhid/blob/53e1a949fc0784af716b782ddfa6c647cafd1f05/src/platform/windows/driver/libvirtualhid.inf.in) grants ordinary authenticated users and Everyone read/write/execute access to that device interface. Other gamepad profiles submit reports through [VHF](https://github.com/LizardByte/libvirtualhid/blob/53e1a949fc0784af716b782ddfa6c647cafd1f05/src/platform/windows/driver/libvirtualhid_umdf.cpp), whose HID collections are [discoverable by ordinary applications](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/finding-and-opening-a-hid-collection). A broker token protects feeder operations, not each game's device read. Installing the driver/broker and accepting a paid license would each require a separate owner decision, and the reviewed path still lacks parent exclusion.

**Enforcement finding:** Sunshine client IDs, ViGEm serials, XInput slots, broker tokens, feeder PIDs and the same-user SID do not bind gamepad consumption to the exact child logon generation. The broadly open libvirtualhid XUSB interface and token-free state path are direct consumer-side evidence, beyond merely finding no WTS parameter. ViGEm publishes PnP devices without an inspected child-consumer filter. Unmeasured Windows/RDP behavior remains possible; it cannot be presumed either safe or impossible.

## Single recommended discriminating experiment

First complete separately approved Stage A/B on an independent Windows 11 Pro target. The intended workstation's owner-supplied elevated read-only child-feature result remains False, and its connected-network Stage A remains No-Go because unexpected RDP exposure and parent sign-in interference are unresolved. The controller test requires a real exact-identity child desktop and a separate approval for a free ViGEmBus installation if absent on the independent target. It does not require GPU capture or Moonlight: a short synthetic report feeder may isolate the Windows routing question. No such test is authorized on the protected workstation.

1. Record exact parent and child WTS IDs and logon times, provider version, two actual PnP target instance IDs and pre-test controller baselines. The existing read-only ChildStreamControllerWitness.exe records XInput slots but does not itself attribute a slot to a PnP instance; establish that link independently before calling any result ChildStream-owned.
2. In the exact child, create only two ViGEm targets with distinct serials. Pulse distinct buttons on A and B separately. Observe both sessions simultaneously through the existing witness, and through a HID/DirectInput consumer if the intended game uses that API. Change parent focus. Require both independent pulses in the child and neither target/report in the parent; exclude pre-existing controllers by instance identity.
3. Repeat after feeder disconnect/reconnect and after a new verified child logon generation. Never inherit an old serial or XInput slot. Unplug only the two owned targets and verify their disappearance and preservation of baseline devices.

If a parent process sees either target or pulse, reject this free provider path even if the child also works. If the parent does not, the result is only a measured Windows/RDP candidate behavior; validate the actual game's input API and repeat focus/reconnect before enabling production controllers. If identity attribution is ambiguous, classify the experiment inconclusive. A negative result requires a separate owner decision about a truly session-scoped device/redirection mechanism or a revised architecture. No custom driver, game hook, paid provider, permanent elevated service or virtualization redesign is authorized by this decision.

The [HidHide path allow-list](https://docs.nefarius.at/projects/HidHide/API-Documentation/) cannot distinguish identical game executable paths in parent and child sessions and changes global visibility. It is not a fallback. The existing witness uses [XInputGetState](https://learn.microsoft.com/en-us/windows/win32/api/xinput/nf-xinput-xinputgetstate) and records its own process/session/logon time and four slots without injecting input. Its synthetic tests check interpretation, not child-only routing.
