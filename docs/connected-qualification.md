# Connected feature setup: qualification and recovery boundary

This path is source-complete for a first, separately approved Stage A feature operation. It has **not** qualified the intended workstation. The independently measured packet evidence and child-session behavior below are still missing. ChildStream never signs out the parent automatically.

## Two evidence stages

1. **Before feature enablement:** A separate approval applies the two exact ChildStream-owned, non-loopback inbound TermService block rules. The normal setup form then makes a version 7 connected plan. A native time-filtered, read-only Windows Security query looks for inbound WFP 5152/5157 drops on the configured RDP port, with `FilterOrigin` equal to each exact owned TCP/UDP rule. Each assigned non-loopback address on each relevant physical or attributed guest-facing interface needs one unique TCP and one unique UDP record of the same address family. A dual-stack interface needs both families; multiple addresses within a family need distinct records. Scoped IPv6 link-local addresses require exact scope in both interface and event evidence. Mapped IPv6/IPv4 aliases and ambiguous scopes cannot qualify. The record must be newer than the owned containment journal and within the ten-minute observation window. Any addressed virtual, tunnel, or other interface whose path cannot be attributed rejects qualification. The helper verifies the original feature is disabled, ordinary-RDP policy denies connections, listeners are absent, owned rules are effective in ActiveStore, and the probe plan and network/firewall fingerprints agree. A closed socket or a rule's mere presence does not count as a packet drop.
2. **After a new, separate feature-operation approval:** The helper consumes that exact reviewed record before creating the probe journal. A further exact-plan approval is required for `PrepareFeature`; it performs at most one journaled `WTSEnableChildSessions(true)` attempt. The operator may need a one-time fresh physical-console sign-in. `VerifyStageA` separately checks the actual WTS no-child result and unchanged policy, listener, network and owned-rule state. Error 1168 or a changed listener is not a positive result. A real child-loopback desktop connection needs **another** Stage B approval and observation; it cannot be required as pre-enable proof.

The version 2 pre-feature record includes Windows MachineGuid, requesting-account hash, Windows build, exact containment journal and feature plan hashes, original network/firewall fingerprints, active interface identities/addresses, per-address coverage count, Security event record IDs and timestamps, and a ten-minute expiry. Older version 1 evidence may be retired during recovery but cannot authorize a feature write. The helper stores it only in the protected requester directory. `Capture packet proof` records a pending hash; `Review proof hash` requires independent human review of that exact hash. `Begin approved plan` and `Enable feature` re-read the native event records and current state, reject replay and drift, and never accept a user-supplied Boolean as packet proof. The Security query filters by native `TimeCreated`, counts only events in the exact managed window, rejects current-window overload, unavailable timestamps/records, future records, log-clear event 1102, and malformed relevant events. Old history cannot consume the 4,096-current-record limit. Unavailable or incomplete event history never supplies coverage. The standalone connected feasibility CLI has no new mutating entry; its old connected mutation commands are refused. Its legacy restore path remains for historical recovery.

## Stop and restoration

If capture or review fails before `Begin approved plan`, the feature is still disabled and there is no feature journal. Leave the containment rules in place while inspecting the reason; retire an exact pending/reviewed record under the current closed-RDP baseline, then separately recover the owned rules if desired. After a begun plan, inspect the requester journal. If feature enablement is ambiguous or a listener/service changes, retain containment and use reviewed exact-state recovery. `Restore original` checks child absence and the original feature state before marking the probe journal restored. Only then can the exact qualification record be retired and the owned rules removed. Interrupted retirement is retried only against identical private bytes; a conflicting copy blocks. Uninstall refuses active qualification, containment, or unrestored probe journals.

## Current qualification limit

The pre-feature WFP events are not known to exist on the intended PC. The owned rules are scoped to **TermService**, while ordinary RDP policy denies connections and the current baseline has no RDP listener. A remote connection failure to an absent listener does not prove these rules blocked the packet. It is unverified whether Windows will attribute a drop to these service-scoped rules before a service socket exists. The helper does not enable auditing, ordinary RDP, or a test listener to manufacture proof. Security event auditing may itself be disabled. A concrete qualification would require the exact owned rules effective, auditing already available or separately approved, and separately approved external/guest TCP and UDP test traffic to every assigned address; the native reader would then need the exact owned-rule drops. The test traffic must come from outside the host's loopback path, for example an operator-controlled phone on the LAN for the physical path, and from an independently attributed guest path for guest addresses. A timeout or another filter's drop is inconclusive.

The native classifier now reads only Hyper-V switch metadata and management-OS host ports through documented Windows cmdlets. A uniquely matched MAC, port ID, switch ID/name, internal/private switch, and exact `vEthernet (...)` adapter identity (including Windows' `#2` description suffix) labels an interface **Guest**, meaning it gains mandatory per-address packet obligations. It is not declared harmless. Duplicate or mismatched identity and external switches remain Unknown. This source path has not run on the intended PC. Its active Tailscale tunnel remains unmatched and Unknown by the recorded evidence, so the connected feature gate still rejects the present topology without interfering with it. Native host-port attribution alone cannot establish guest packet reachability or rule enforcement.

**Recommended owner decision before any host qualification:** Decide whether to review a short-lived, exact-owned inbound TCP/UDP block for the configured ordinary-RDP port on all programs, with non-loopback remote scope, in place of the current TermService-scoped block for an explicitly authorized experiment. This is an existing Windows Firewall rule shape, not a new driver or service. It could cause a pre-listener packet to match a port filter, but that behavior and loopback compatibility must be observed; source analysis does not certify it. The proposed test requires a read-only baseline of actual RDP port ownership, audit availability, effective firewall policy, all relevant interfaces including the Tailscale tunnel, and a recovery plan retaining the block until feature/listener restoration is verified. Separately approved phone/guest packet probes would seek exact filter-origin events before any feature write. A matching drop on every required address/protocol is necessary but not by itself proof of all future traffic; missing, differently attributed, or unavailable records leave admission closed. No broader rule or packet test is implemented or authorized by this source increment.

Consequently **no connected Stage A feature write is admitted on the current PC by present evidence**. The remaining native prerequisite is an approved, noninterfering acquisition of attributable packet denial across the Tailscale and guest paths, or a separately reviewed rule-scope change with that same coverage. Stage B, GPU, Sunshine, controller, audio and Fire TV behavior remain physically unverified.

Microsoft documents Windows 11 WFP 5152/5157 `Filter Origin` and `Interface Index` fields in its [filter-origin audit documentation](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/filter-origin-documentation). Its documentation also states that auditing those events may require enabling the relevant audit policy. ChildStream does not change that policy automatically.
