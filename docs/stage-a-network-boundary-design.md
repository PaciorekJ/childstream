# Stage A network boundary: diagnostic and proposed acceptance rule

**Historical shared-host analysis; not an execution route for that workstation.** `scripts/network-boundary-diagnostic.ps1` is read-only but inspects shared guest and networking state, so do not run it on the protected workstation for ChildStream. The permanent [scope boundary](scope-boundary.md) blocks workload or network interruption there. The existing `plan-isolated` gate rejects active non-loopback infrastructure; version 5 `plan-boundary` accepts only when all offline predicates pass on a separate dedicated target. No host action is authorized by this document or a generated hash. Keep raw reports, addresses and fingerprints private; do not attach them to PR or CI. The dedicated-target strategy is in [stage-ab-physical-window.md](stage-ab-physical-window.md).

## Three separate questions

| Condition | Evidence required for a later gate | Failure meaning |
| --- | --- | --- |
| External isolation | A second operator confirms physical cable, Wi-Fi radio, Bluetooth PAN, USB/cellular tether and other uplink severance. Read-only adapter, address and route inventory in every compartment corroborates this. Every active virtual path has a verified underlay and switch/bridge/NAT attribution. | An active physical link, external/bridged switch, alternate uplink, or unknown virtual underlay prevents an offline claim. A default route is not required for local-subnet reachability. A retained route on a disconnected link is investigated, not called an active external path by itself. |
| Internal guest paths | Enumerate Hyper-V VMs and their switch ports, WSL2 distributions and effective NAT/mirrored mode, HNS networks, Docker containers and published host bindings. Map host vEthernet ports to switch identity through Hyper-V/HNS data, not names. | An Internal switch permits guest-to-host traffic. An active guest or unknown peer inventory prevents assuming the host is isolated from local guests. |
| RDP exposure during feature enablement | Baseline ordinary RDP policy denied, `TermService` stopped, inspected TCP/UDP endpoints absent, and unchanged firewall profiles/rules. Either prove every active guest path denies an unexpectedly started RDP listener or keep all guest peers quiescent throughout the feature write, fresh logon and restoration. | A listener can appear between checks. The existing 20 potentially permissive and six unknown firewall classifications remain connected-network blockers and do not prove guest-source RDP denial. |

Microsoft documents that an **Internal** Hyper-V switch connects guests to the host, and that NAT can use an Internal switch. WSL2 NAT guests can address the Windows host through their gateway; mirrored mode can also connect over localhost. Docker host port publication can bind all interfaces. These are distinct from an external physical uplink. [Hyper-V switch types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology), [Hyper-V NAT](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/create-a-virtual-switch-for-hyper-v-virtual-machines), [WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking), [Docker port publishing](https://docs.docker.com/reference/cli/docker/container/run/).

The actual host report is private and must be reviewed separately. A WSL NAT gateway, Docker-published host ports, or an Internal switch each establishes a path to investigate; none proves that a future RDP listener is filtered. An empty `Get-NetNat` result cannot certify the HNS path. An access-denied Hyper-V/HNS query is unknown, never an empty VM or switch list. No host-specific addresses, ports, peer identities or topology fingerprint are stored here.

## Current diagnostic

From the physical console, with no elevation required for the attempt:

```powershell
pwsh -NoProfile -File .\scripts\network-boundary-diagnostic.ps1
```

It emits `ChildStream.NetworkBoundaryDiagnostic.v1` JSON with one `Pass`, `Fail` or `Unknown` verdict for each predicate, four separate condition summaries, a network fingerprint only when all required sources are readable, and `StageAPlanAuthorized=False`. It reads the existing feasibility inventory, adapters, Hyper-V switches and management/VM ports, HNS networks/endpoints, NetNat, portproxy registry entries, bridge bindings, IP forwarding, WSL state, Docker processes and published container bindings. A successful `Get-NetNat` with no objects does not satisfy the HNS/bridge predicate. It never launches a stopped WSL distribution to learn its networking mode. Access errors become `Unknown`; an adapter name is only a local label, never an allow rule. An addressed management-OS vEthernet adapter is attributed through a unique MAC, virtual-adapter description and matching Hyper-V host-port switch ID **and** name; unrelated miniports do not need a PnP property. An unaddressed active virtual adapter needs no observed address or route and a fully inspected, disabled bridge binding. An addressed tunnel, including Tailscale, remains `Unknown` until its underlay graph is independently proven. A retained route on a physical adapter with an independently observed disconnected link is recorded but not called active exposure; reconnecting that link fails the next check.

The elevated source-shape report at `d6ed0a3f74a8f43477fff3b2f93554836ed9e2cd` confirmed that **all 12 relevant adapters** completed escaped-name, full-binding enumeration with zero failures. The earlier wildcard `Get-NetAdapterBinding` query returned only `CimJobException`, so the exact leaf cause was not captured; the successful per-adapter query establishes that no currently relevant individual adapter fails the narrowed read. The collector never treats an uninspected binding as absent. Relevant means physical, up or having an observed IP address/route. The private diagnostic retains failed interface indices, error IDs, HRESULTs and available nested CIM status for future failures. [Get-NetAdapterBinding](https://learn.microsoft.com/en-us/powershell/module/netadapter/get-netadapterbinding?view=windowsserver2025-ps).

The diagnostic fingerprint covers the full collected topology, guests, forwarding, RDP/firewall evidence and operator severance confirmation. Item-order changes do not change it; HNS or firewall changes do. It is `null` if any required source is inaccessible or the adapter snapshots disagree. Contradictory graph records produce separate `Unknown` predicates, including HNS endpoint-to-network ID conflicts. `BlockingFindings` separates current-state failures, topology evidence gaps and later operator checks. The v5 probe now consumes a single private boundary/inventory capture, checks relevant bridge-query coverage independently, recomputes its own fingerprint of the complete observation, and binds it into the exact plan hash and durable journal. It rereads before feature enablement, after the API call, after fresh logon, during restoration, and before reconnect assessment. Existing v3/v4 journal readers and the connected-network firewall gate remain intact. These are offline-tested source properties, not live host acceptance.

Quitting Docker Desktop can make `docker ps` unavailable. The collector now distinguishes a recognized **daemon-unavailable** error from permission denial or an unknown error. It reports `VerifiedStopped` only when separate Windows Docker-process, WSL distribution, HNS endpoint, portproxy, bridge/IP-forwarding and Docker-owned TCP/UDP listener reads are complete and show no remaining peer or forwarding path. The v5 parser independently rechecks that corroboration. An unavailable daemon by itself never supplies a zero-container observation. This is a source-level rule tested with deterministic scenarios; the host has not been paused to validate it live.

The later isolated rehearsal may use `-OperatorConfirmedPhysicalSeverance` only after two local observers actually inspect cables, radios and tethering. `-ExpectedNetworkFingerprint <PRIVATE_BASELINE>` reports drift across a fresh logon; this diagnostic hash is **not** the existing probe's plan hash or journal binding. Run its deterministic synthetic tests with `pwsh -NoProfile -File .\tests\NetworkBoundaryDiagnosticTests.ps1`.

The current Codex console has protocol type 0, but its constrained token cannot read several CIM, Hyper-V, HNS, WSL and Docker sources. The inbox `HostNetworkingService` module is discoverable through Windows PowerShell 5.1 rather than `pwsh` on this machine; the diagnostic calls a separate read-only Windows PowerShell bridge with process-scoped `RemoteSigned` execution policy. The latest already elevated same-account physical-console report measured two internal switches, two management-OS ports, zero registered VM ports, two HNS networks and one endpoint. All relevant bridge reads, the host-port graph, HNS endpoint graph and RDP baseline passed. Connected Wi-Fi, active internal guests/HNS endpoint, Docker forwarding and unresolved virtual-path attribution still block Stage A. The latter remains Unknown until an offline, quiescent snapshot; no raw identities or addresses are needed in the PR. Any firewall classification retained in the connected-network gate remains unchanged.

## Version 5 acceptance rule and remaining live gate

1. The v5 plan binds a private topology snapshot to its exact hash and journal: physical adapter identity/state, IP interfaces/addresses/routes in all compartments, switch type and host/guest port IDs, NAT/HNS/bridge/portproxy state, active guests, Docker bindings, RDP policy/listeners/TermService, firewall classification, and operator confirmation. A name or absence of a default route is insufficient. Missing source or contradictory mapping fails closed.
2. Permit an active Internal/Private switch or host vEthernet only when its switch/port identity is independently established, it has no external bridge/underlay, and no active guest can reach the host during the experiment. An unaddressed Windows miniport is not automatically external exposure; verify it has no IP path, bridge membership or active peer. A VPN tunnel with no independently verified external underlay does not itself prove outside reachability, but its route and service state remain bound and rechecked.
3. If any WSL2, Docker, Hyper-V or other guest remains active, require a path-specific, read-only proof that an unexpected RDP listener cannot be reached from that guest through host vEthernet, NAT, mirrored localhost, port forwarding or bridge paths. Reassess all 20 potentially permissive and six unknown rules against guest source ranges, active profiles, interface scopes and the configured RDP port. **Do not presume the current rules provide that proof.**
4. The v5 probe rechecks all conditions immediately before the feature write, after the non-atomic API call, at fresh parent logon, before any further progression, and before restoration/reconnection. Any uplink, guest, forwarding, listener or fingerprint drift stops progression and is recorded in the journal. It cannot create a child session in this posture. A sequence of snapshots cannot prove continuous safety by itself; a local observer maintains the physical boundary between checks.
5. Keep the connected-network firewall gate unchanged. Restore the exact original feature state while physically offline. If `TermService` or an RDP endpoint changed, or restoration is ambiguous, preserve the journal and remain offline until separately reviewed recovery. Reconnection requires explicit verified feature restoration and a closed RDP posture.

## Operator boundary

The historical shared-host snapshot is **No-Go**. Workload quiescence and network disconnection of that workstation are excluded, even if a diagnostic could theoretically pass afterward. The current source accepts a version 5 plan only with complete `External=Pass`, `GuestPath=Pass`, `RdpExposure=Pass` and `virtual-paths-attributed=Pass` on a separate dedicated target; unknown sources remain blockers. An independent no-NIC Windows VM can use the new v6 strict plan for separately approved Stage A/B without claiming that the v5 collector has inspected absent host infrastructure. Published v4 strict journals remain Stage A only. See the [independent target procedure](stage-ab-physical-window.md) and [environment requirements](independent-test-environment.md).
