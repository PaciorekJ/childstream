# Stage A network boundary: diagnostic and proposed acceptance rule

**Preparation only.** `scripts/network-boundary-diagnostic.ps1` is read-only and cannot authorize Stage A. The existing `plan-isolated` gate remains unchanged and still rejects active non-loopback infrastructure. No child-session feature write or Windows networking change is authorized by this document. Keep raw reports, interface addresses, container details and fingerprints private; do not attach them to the PR or CI.

## Three separate questions

| Condition | Evidence required for a later gate | Failure meaning |
| --- | --- | --- |
| External isolation | A second operator confirms physical cable, Wi-Fi radio, Bluetooth PAN, USB/cellular tether and other uplink severance. Read-only adapter, address and route inventory in every compartment corroborates this. Every active virtual path has a verified underlay and switch/bridge/NAT attribution. | An active physical link, external/bridged switch, alternate uplink, or unknown virtual underlay prevents an offline claim. A default route is not required for local-subnet reachability. A retained route on a disconnected link is investigated, not called an active external path by itself. |
| Internal guest paths | Enumerate Hyper-V VMs and their switch ports, WSL2 distributions and effective NAT/mirrored mode, HNS networks, Docker containers and published host bindings. Map host vEthernet ports to switch identity through Hyper-V/HNS data, not names. | An Internal switch permits guest-to-host traffic. An active guest or unknown peer inventory prevents assuming the host is isolated from local guests. |
| RDP exposure during feature enablement | Baseline ordinary RDP policy denied, `TermService` stopped, inspected TCP/UDP endpoints absent, and unchanged firewall profiles/rules. Either prove every active guest path denies an unexpectedly started RDP listener or keep all guest peers quiescent throughout the feature write, fresh logon and restoration. | A listener can appear between checks. The existing 20 potentially permissive and six unknown firewall classifications remain connected-network blockers and do not prove guest-source RDP denial. |

Microsoft documents that an **Internal** Hyper-V switch connects guests to the host, and that NAT can use an Internal switch. WSL2 NAT guests can address the Windows host through their gateway; mirrored mode can also connect over localhost. Docker host port publication can bind all interfaces. These are distinct from an external physical uplink. [Hyper-V switch types](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/features-terminology), [Hyper-V NAT](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/create-a-virtual-switch-for-hyper-v-virtual-machines), [WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking), [Docker port publishing](https://docs.docker.com/reference/cli/docker/container/run/).

The actual host report is private and must be reviewed separately. A WSL NAT gateway, Docker-published host ports, or an Internal switch each establishes a path to investigate; none proves that a future RDP listener is filtered. An empty `Get-NetNat` result cannot certify the HNS path. An access-denied Hyper-V/HNS query is unknown, never an empty VM or switch list. No host-specific addresses, ports, peer identities or topology fingerprint are stored here.

## Current diagnostic

From the physical console, with no elevation required for the attempt:

```powershell
pwsh -NoProfile -File .\scripts\network-boundary-diagnostic.ps1
```

It emits `ChildStream.NetworkBoundaryDiagnostic.v1` JSON with one `Pass`, `Fail` or `Unknown` verdict for each predicate, four separate condition summaries, a network fingerprint only when all required sources are readable, and `StageAPlanAuthorized=False`. It reads the existing feasibility inventory, adapters, Hyper-V switches and management/VM ports, HNS networks/endpoints, NetNat, portproxy registry entries, bridge bindings, IP forwarding, WSL state, Docker processes and published container bindings. A successful `Get-NetNat` with no objects does not satisfy the HNS/bridge predicate. It never launches a stopped WSL distribution to learn its networking mode. Access errors become `Unknown`; an adapter name is only a local label, never an allow rule. An addressed management-OS vEthernet adapter is attributed only through a unique MAC plus Hyper-V host port/switch relationship and the Hyper-V virtual-adapter PnP identity. An addressed tunnel, including Tailscale, remains `Unknown` until its underlay graph is independently proven. An unaddressed virtual adapter can be classified only when it has a PnP identity, no observed address or route, and no enabled bridge binding. These conditions are intentionally conservative and may require refinement after a privileged read-only topology inventory.

The diagnostic fingerprint now covers the full collected topology, guests, forwarding, RDP/firewall evidence and operator severance confirmation. Item-order changes do not change it; HNS or firewall changes do. It is `null` if any required source is inaccessible or the adapter snapshots disagree. Contradictory graph records produce separate `Unknown` predicates. The bridge-binding query is an added observation, not yet proof that every Windows bridge mechanism is covered; that coverage also needs real source-schema review. The fingerprint remains separate from the existing Stage A v4 plan hash and **is not yet bound to a mutating probe journal**. No existing v4 journal format or strict enforcement path was changed. Promoting this evidence into a versioned Stage A plan requires a distinct compatibility review after the real source schemas can be observed. The current source-only increment therefore cannot authorize Stage A.

The later isolated rehearsal may use `-OperatorConfirmedPhysicalSeverance` only after two local observers actually inspect cables, radios and tethering. `-ExpectedNetworkFingerprint <PRIVATE_BASELINE>` reports drift across a fresh logon; this diagnostic hash is **not** the existing probe's plan hash or journal binding. Run its deterministic synthetic tests with `pwsh -NoProfile -File .\tests\NetworkBoundaryDiagnosticTests.ps1`.

The current Codex console has protocol type 0, but its constrained token cannot read several CIM, Hyper-V, HNS, WSL and Docker sources. A recent non-elevated diagnostic returned `Unknown` for all four conditions and no eligible plan. That is a collector-access result, not a measurement of an isolated machine. An already elevated same-account physical-console read-only inventory is the next evidence gate; do not elevate automatically and do not treat access denied as an empty switch, VM, endpoint or guest list. Any firewall classification retained in the existing connected-network gate remains unchanged.

## Acceptance rule to implement before Stage A approval

1. Bind a versioned topology snapshot to the exact plan and private journal: physical adapter identity/state, IP interfaces/addresses/routes in all compartments, switch type and host/guest port IDs, NAT/HNS/bridge/portproxy state, active guests, Docker bindings, RDP policy/listeners/TermService, firewall classification, and operator confirmation. A name or absence of a default route is insufficient. Missing source or contradictory mapping fails closed.
2. Permit an active Internal/Private switch or host vEthernet only when its switch/port identity is independently established, it has no external bridge/underlay, and no active guest can reach the host during the experiment. An unaddressed Windows miniport is not automatically external exposure; verify it has no IP path, bridge membership or active peer. A VPN tunnel with no independently verified external underlay does not itself prove outside reachability, but its route and service state remain bound and rechecked.
3. If any WSL2, Docker, Hyper-V or other guest remains active, require a path-specific, read-only proof that an unexpected RDP listener cannot be reached from that guest through host vEthernet, NAT, mirrored localhost, port forwarding or bridge paths. Reassess all 20 potentially permissive and six unknown rules against guest source ranges, active profiles, interface scopes and the configured RDP port. **Do not presume the current rules provide that proof.**
4. Recheck all conditions immediately before the feature write, after the non-atomic API call, at fresh parent logon, before any further progression, and before restoration/reconnection. Any uplink, guest, forwarding, listener or fingerprint drift stops progression and is recorded in the journal. Do not create a child session. A background-free snapshot cannot prove continuous safety by itself; a local observer maintains the physical boundary between checks.
5. Keep the connected-network firewall gate unchanged. Restore the exact original feature state while physically offline. If `TermService` or an RDP endpoint changed, or restoration is ambiguous, preserve the journal and remain offline until separately reviewed recovery. Reconnection requires explicit verified feature restoration and a closed RDP posture.

## Proposed operator-controlled rehearsal sequence (separate approval required)

1. Save work and capture a **private** pre-isolation report, the original Wi-Fi/Ethernet/tether/Tailscale states, switch and HNS topology, running WSL distributions, Docker containers and published ports, Docker Desktop auto-start setting, and original RDP/firewall/feature state. Use read-only `Get-VM`, `Get-VMSwitch`, `Get-VMNetworkAdapter -ManagementOS`, `Get-HnsNetwork`, `Get-NetNat`, `netsh interface portproxy show all`, `wsl --list --verbose`, `docker ps`, and the diagnostic. Hyper-V/HNS queries may need an already elevated same-account console; do not infer an empty result from access denied.
2. If active guests cannot be proven RDP-inaccessible, arrange an approved graceful pause: save work in each active WSL distribution, review all active containers for stateful services and unsaved data, stop them through their owning workflow, Quit Docker Desktop, and terminate only the remaining active distributions after work is saved. Verify WSL and Docker are stopped and no Hyper-V guest/other peer remains. If Docker will auto-start at fresh logon, capture and separately approve a reversible prevention method **before** feature enablement; otherwise stop here. Never terminate workloads automatically from the diagnostic or probe.
3. With a second local observer, unplug physical Ethernet and USB/tether paths, turn off Wi-Fi/Bluetooth/cellular radios, and verify no alternate physical uplink. Reinspect every adapter, interface, address and route; switch types and ports; HNS/NAT/bridges/portproxy; WSL/Docker/VM state; and RDP baseline. Internal host-only adapters may remain only after their paths and peer absence are verified. Tailscale may remain installed; an active tunnel route requires proof that every external underlay is severed. An unreadable query is a stop.
4. Run the diagnostic with the literal operator confirmation and keep its JSON and fingerprint private. The current strict `plan-isolated` must still reject the retained host-only adapters. Do not attempt `begin-isolated` until the proposed gate is separately implemented, offline-tested, reviewed, and its exact plan hash approved.
5. For a later approved Stage A, recheck just before enablement and across fresh logon, including whether Docker/WSL auto-started. If any guest or external path reappears, stop progression while physically offline. Restore the original feature under the existing reviewed recovery rules, verify no unexpected service/listener exposure, then manually restore each network/workload item from the original-state record after reconnect approval.

If guest quiescence cannot be maintained across fresh logon without disruptive host changes, retain **No-Go** for physical-host Stage A. The smallest alternative is an approved disposable Windows 11 VM with its guest NIC disconnected from every switch, VMConnect Basic Session Mode, and a checkpoint before mutation. That alternative still requires suitable host storage and separate VM/test authorization.
