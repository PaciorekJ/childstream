# Independent Stage A/B feasibility target

**The shared workstation is blocked for Stage A/B.** Its active guest paths and addressed tunnel cannot be removed for ChildStream: the [permanent scope boundary](scope-boundary.md) prohibits disturbing unrelated work or shared services. This document is for a **separate Windows environment only**. It authorizes no VM creation, Windows feature change, sign-out, session test, network change or installation.

No such independent environment is currently available. The [minimum environment decision](independent-test-environment.md) identifies no-purchase options and the hardware floor; none has been demonstrated safe and available yet.

## Target selection

**Preferred: a separate physical Windows 11 Pro test PC.** It must have no protected workloads or shared networking dependencies. This gives real child-session, display and GPU evidence without interrupting the development workstation. Later Fire TV, controller, audio and Sunshine testing still needs a separately reviewed, scoped network posture. Results on this PC do not automatically qualify another PC's GPU or display topology.

**Earlier API test: a disposable Windows 11 Pro VM on an independent virtualization host.** Prefer the same Windows build as the intended product host when a licensed image is available. Plan a Generation 2 VM with roughly four vCPUs, 8 GB RAM, at least 64 GB of virtual disk, Secure Boot and virtual TPM. Do not attach a NIC to any external, Default, Internal or Private switch for the feature experiment. Use VMConnect **Basic Session Mode** and verify inside the guest that the process is in the active guest console with protocol type 0; Enhanced Session Mode uses RDP. Take a checkpoint before the first guest mutation and retain the original guest inventory. [Microsoft VM creation prerequisites](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/create-a-virtual-machine-in-hyper-v), [generation 2 security](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/learn-more/Generation-2-virtual-machine-security-settings-for-Hyper-V), [VMConnect session modes](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/enhanced-session-mode), [checkpoint limits](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/checkpoints).

A VM on the protected workstation is **not** presumed independent: CPU, RAM, disk I/O and Hyper-V activity can affect running work even with a disconnected NIC. It is outside the current execution path and would need a separate noninterference assessment and explicit authorization. Do not enable Hyper-V, alter a switch or run a VM there as an implicit substitute.

## Read-only lab qualification

Transfer the exact reviewed ChildStream source by an offline medium or other separately approved route. In the dedicated target, verify SHA and clean tree, run `pwsh -NoProfile -File .\tests\offline.ps1`, then use the read-only `scripts/feasibility-inventory.ps1` and `plan-isolated` with a physically verified no-network guest or machine. Keep raw reports and the plan hash private. The new v6 strict plan requires no active non-loopback address, route or interface; any unknown source, child feature, console identity, RDP policy, service, listener or firewall observation is No-Go. The connected-network firewall gate stays intact.

Published **v4 strict-isolation journals remain readable but Stage A only**. New strict plans use v6, whose journal has a mandatory reviewed-child-teardown field and supports separately approved Stage A-to-B progression. If the independent VM has no Hyper-V/Docker/HNS tooling, do not force the v5 topology collector to treat command failures as empty sources. An accepted v6 plan permits a separately authorized child-feature enable, fresh guest logon, WTS lookup and exact original-state restoration. Error 1168 remains inconclusive. This is the shortest feasible first API test in an independent VM, subject to a passing guest plan.

The v6 strict-isolation extension supplies separate Stage B consent, viewer monitoring, durable exact child identity, interrupted-attempt reconciliation, exact-child teardown and reviewed restoration guards. Existing v4 journals are not reinterpreted as Stage B capable. Offline regressions cover isolation loss and listener drift during connection and recovery. **These are source properties, not evidence that Windows child creation works.** A separate physical lab PC may use the v5 external-boundary journal only if its full topology collector and all gates actually pass; do not install unrelated services merely to fake an empty inventory.

## Mutating test and recovery boundaries

After a passing read-only plan, approve its **exact hash** and one Stage A feature cycle separately. Record the guest's original child-feature value, RDP policy, `TermService`, TCP/UDP listeners, firewall/profile evidence, enumerated sessions and display state. Require an already elevated same-account guest console and an offline sign-in/recovery method. Do not run `begin-*`, `prepare-*`, sign out or connect until those approvals are explicit.

Stage A succeeds only with a fresh parent logon, positive no-child WTS result and independent session enumeration. Stage B remains a separate decision after Stage A; test one loopback ActiveX connection, observe genuinely independent parent/child interaction, and record the exact parent-associated child ID and WTS generation. Do not infer desktop success from a WTS ID. Teardown needs separate exact-child approval. Keep the guest isolated until child absence, original child-feature value, ordinary RDP-denied policy, stopped `TermService`, absent listeners and the original infrastructure state are independently verified. An interrupted or ambiguous operation retains its journal for reviewed recovery; never guess a session ID, repeat an uncertain feature write or reconnect a NIC to clear a failure. A checkpoint is an additional guest rollback path, not evidence that the live restoration logic worked.

Only a positive isolated Stage A/B result warrants the next separately reviewed display/GPU and streaming tests. VM graphics are not physical GPU acceptance. Product acceptance requires a real Windows machine, a scoped network path to Fire TV, and proof that Sunshine, Steam, controllers and audio remain independent while the parent desktop is usable. The protected workstation remains blocked until a coexistence design meets the scope boundary without suspending other work.
