# Guided Moonlight pairing: source boundary

The Windows computer is the intended ChildStream host. A phone or Fire TV running Moonlight is the streaming client; no second computer is required for that role. A separate Windows target is presently needed only for child-session acceptance because the protected development workstation cannot be used for disruptive Stage A/B testing.

The launcher now has a **Pair Moonlight** entry and a guided PIN dialog. It remains disabled until an exact child-session Sunshine process, its private configuration/state, HTTPS certificate and listener ownership have been verified. There is no fallback to the installed native Sunshine service. The source-level pairing coordinator lists pending requests from the pinned Sunshine /api/pin API, displays the reported client name/address, requires one explicit selection and four ASCII PIN digits, rechecks the same pairing ID/name/address and runtime ownership, then submits the exact ID and PIN. A false status, changed request, owner drift or ambiguous response cannot be shown as success. The PIN is not written to project files or logs. The transport and runtime capability are not yet provisioned by the launcher, so this candidate cannot pair or stream.

Before activating the dialog, runtime integration must prove the ChildStream Sunshine executable digest, process PID/start time and child WTS generation, its owned configuration and paired-client state path, selected nondefault port family, HTTPS certificate fingerprint, and current listener PID/port. A request-local pinned TLS transport and admin authentication must address only that endpoint. Pairing is an approval of one Moonlight client; it never authorizes child-session enablement, sign-out, a firewall change, or a Sunshine launch. The user must verify the device in Moonlight against the ChildStream host name and custom endpoint. Discovery and manual custom-port behavior, native Sunshine coexistence, and state persistence across restarts remain physical client tests. Sunshine's configured file_state is intended to retain pairing; the native instance's state must remain separate.

Microsoft documents automatic child-session authentication except when the parent used a smart card or logged in before child sessions were enabled. This is a conditional first-enablement issue, separate from Moonlight PIN pairing. A successful WTS feature query does not establish when the current parent authenticated. The narrow unelevated physical-host query on 2026-10-15 returned Win32 error 5 (access denied); the current feature state is **unknown**. A historical 2026-10-13 inventory observed the feature disabled, but that cannot establish its current value. No elevation or Windows setting change followed. ChildStream must first test existing-session authentication on an authorized target. If first-time feature enablement requires a fresh parent logon, the operator must separately approve a saved-work, offline-sign-in-verified sign-out/recovery plan. No launch or reconnect may sign out the parent automatically. Once the feature and parent authentication are valid, the product should reconnect the same verified child without a new sign-out or PIN, unless live evidence demonstrates a constraint.

The acceptance sequence remains: Stage A WTS result; separately approved Stage B independent desktop; child-owned runtime and native coexistence; secure custom endpoint and pairing; Moonlight desktop stream, reconnect and retained pairing; child-only input/audio and gameplay. Source tests establish only parsing, exact-request selection, fail-closed transitions and UI compilation. They do not establish that a client has connected to ChildStream.
