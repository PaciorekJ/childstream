# Guided Moonlight pairing: source boundary

The Windows computer is the intended ChildStream host. A phone or Fire TV running Moonlight is the streaming client; no second computer is required for that role. A separate Windows target is presently needed only for child-session acceptance because the protected development workstation cannot be used for disruptive Stage A/B testing.

The launcher now starts a verified limited child agent after exact child-session connection. Its explicit **Start ChildStream Sunshine** action uses a dedicated versioned executable, child display/audio observations, a stable private identity directory, and exact PID/listener checks. **Pair Moonlight** then opens a guided PIN dialog only after authenticated, certificate-pinned HTTPS readiness. There is no fallback to the installed native Sunshine service. The pairing coordinator lists pending requests from the pinned Sunshine `/api/pin` API, displays reported client name/address, requires explicit selection and four ASCII PIN digits, rechecks the same ID/name/address and runtime ownership, and submits that exact request. A false status, changed request, certificate drift or ambiguous response is a failure. The PIN is not written to files or logs. This path is tested with substituted child/process/TLS boundaries, not a real Moonlight client.

The transport addresses only the owned loopback listener with dedicated admin credentials and a certificate pinned to ChildStream's stable identity. On first start it uses the pinned release's `/api/password` bootstrap only when the owned Sunshine credential file is absent; credentials are DPAPI-protected for the current user and never copied from native Sunshine. The configured `file_state`, certificate and key remain stable across child generations. Reconnection does not submit another PIN automatically. **The current runtime binds Sunshine to loopback, so a phone or Fire TV cannot yet connect.** A distinct LAN port candidate exists in source, but a reviewed network exposure and coexistence gate must precede any production LAN launch. Pairing never authorizes Windows feature enablement, sign-out, a firewall change or an unrelated Sunshine launch. Discovery/custom-port behavior, native coexistence and state persistence still require physical client testing.

Microsoft documents automatic child-session authentication except when the parent used a smart card or logged in before child sessions were enabled. This is a conditional first-enablement issue, separate from Moonlight PIN pairing. The operator's elevated, read-only physical-console API query on 2026-10-15 succeeded and returned ChildSessionsEnabled=False. It supersedes the earlier unelevated access-denied result; no feature change followed. Enabling the feature during the current parent logon would place that logon in Microsoft's documented exception, so password-free child connection might require one fresh parent sign-in. A Windows sign-out closes applications in that logon session and cannot be treated as noninterfering with protected work. The existing protected workstation is not an approved place to test that transition. No launch or reconnect may sign out the parent automatically. Once the feature and parent authentication are valid, the product should reconnect the same verified child without a new sign-out or PIN, unless live evidence demonstrates a constraint.

The acceptance sequence remains: Stage A WTS result; separately approved Stage B independent desktop; child-owned runtime and native coexistence; secure custom endpoint and pairing; Moonlight desktop stream, reconnect and retained pairing; child-only input/audio and gameplay. Source tests establish only parsing, exact-request selection, fail-closed transitions and UI compilation. They do not establish that a client has connected to ChildStream.
